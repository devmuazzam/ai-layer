# Samsara link, asset field security and the DMV make code (Brian Petros, 2026-11-13)

**Context.** There is no ticket. Brian Petros emailed Patrick McKiernan on 2026-11-12 about
cleaning up Samsara asset data, and that email was shared with CodingCops. Syed Haris replied the
same day with three questions. They are summarised, not quoted, in
[../assets/samsara-data-audit-and-edit-access-brian-2026-11-12.md](../assets/samsara-data-audit-and-edit-access-brian-2026-11-12.md) §4:

1. Who fills in Samsara's External IDs? Is it the ERP, using a token from Patrick that can edit
   vehicles, or TCG by hand?
2. Should the ERP's core identity fields be limited to the same short list of editors? Does a
   change need approval, or only a record?
3. Does the DMV make code go on every vehicle, or only on registered units?

Brian's reply is recorded verbatim in
[../assets/samsara-cleanup-plan-and-answers-brian-2026-11-13.md](../assets/samsara-cleanup-plan-and-answers-brian-2026-11-13.md)
§1–§3, beside what the code does today for each point. That file is the full text. This note
quotes it only as needed.

### Q3: two contradictions inside the reply, both open

Each pair of statements comes from Brian's own reply. **Neither statement in a pair wins.** The
later paragraph is more detailed, but that does not make it his final word.

1. **What makes the field appear.** He says *"we might need a checkbox for the user to select if
   it is to be registered"*. He also says *"Required when a plate exists … hidden otherwise"*.
2. **Where the value comes from.** He says *"simply display … for reference, but would simply pull
   (or be driven from) the selected Make"*, which makes it read-only and derived from Make. He also
   says *"It should be entered from the registration card, with a suggested default from the Make
   list and a flag if they differ"*, which makes it entered by a person, pre-filled, and checked
   against Make.

## Why

Brian gave reasons for two of the answers:

- **The two-way link and the daily check:** *"Samsara reads the VIN directly from the engine, so we
  should also check linked vehicles where the VIN in ERP no longer (or doesn't match) the VIN in
  Samsara."* The check exists to catch the kind of drift his cleanup found, such as moved gateways
  and wrong VINs.
- **Field-level control and history:** his 2026-11-12 email to Patrick asked to *"lock this down"*
  so that core asset data does not change *"without proper approval from the ones responsible for
  maintaining/certifying it"*. He says the ERP version is *"Similar to payroll"*, meaning the same
  kind of field-specific security.

For Q3 he gave no reason.

## What this does not settle

1. **Who holds the Asset Data Admin role.** He had deferred this to Joe Schacatano and Kyle Harlow
   on 2026-11-12, and they have not answered. His suggested five names (Kyle Harlow, Joe
   Schacatano, Jeff Stricker, Brian Petros, Patrick McKiernan) were for **Samsara**, and they are
   a proposal.
2. **Multiple roles per user (Q2a)** against the 2026-10-20 *one main role decides access*. Two
   related points are also open:
   - **Who assigns the role.** Brian's *"We assign specific users to that role"* does not say who
     "we" is. Under the 2026-10-20 decision (F2), the Dispatcher assigns roles and the Dispatch
     Manager approves.
   - **Per-person access beyond the role default** is already open in
     [../admin/gaps.md](../admin/gaps.md#per-person-access-beyond-the-role-default-and-the-approval-flow-for-role-and-permission-changes),
     awaiting Ryan Adams. Brian's add-on role is another way to meet the same need.
3. **Tentative items (Q2b):** finance and accounting fields, control over documents, and a
   separate card or section.
4. **Readings that a developer could get wrong:**
   - **"Admins".** Whether *"the other admins"* and *"a second admin"* mean holders of Asset Data
     Admin or system administrators. The first is the natural reading, but he did not say.
   - **"Retiring".** Whether *"retiring"* is the existing archive action. No merge of asset
     records exists yet.
   - **VIN validation scope.** Whether it applies to every asset that has a VIN, including
     equipment with no 17-character VIN.
   - **"With engines".** What counts as an asset *"with engines"* for check (b). Nothing in the
     vault or the code defines it.
5. **Q3's two contradictions**, above.
6. **Q1's remainders:**
   - **Samsara token.** Whether Patrick McKiernan's token can write. Not checked.
   - **Initial links.** Whether the ERP also writes External IDs for the initial links Brian
     supplies, or only for links made in the picker.
   - **Unlinking.** What happens to the External ID when a link is changed or removed.
   - **One device, two assets.** A crane and its support tractor on one device. Raised in the
     cardinality entry of [../assets/gaps.md](../assets/gaps.md); not addressed.

## Build impact

No code is changed by this note. The 11-13 file's tables show what each answer means against the
code as read on 2026-11-13. In short:

- **Q1.** Needs new work: a **write to Samsara** (blocked until the token is confirmed), a picker
  limited to unlinked vehicles (only partly checked), and the **daily check with notification**.
  `Asset.samsaraAssetId` already holds Samsara's ID.
- **Q2.** Needs field-level permissions, which do not exist today. One `asset-management: edit`
  covers every field. It also needs the reason, photo and notification step, second-admin
  approval, VIN validation and a duplicate-VIN block. Already built: the change log for asset
  edits and the duplicate-Samsara-link block. Any field-level work should wait for item 2 above,
  because whether it is built as a second role or as a permission on the one main role depends on
  that answer.
- **Q3.** Needs a make-code configuration table and a Registration section. Do not build the
  visibility or value-source behaviour until the two contradictions are answered.
