# Samsara cleanup plan, and Brian's answers (2026-11-13)

This is Brian Petros's reply to the three questions CodingCops sent on 2026-11-12
([samsara-data-audit-and-edit-access-brian-2026-11-12.md](samsara-data-audit-and-edit-access-brian-2026-11-12.md) §4).
It holds two different kinds of content:

- **§1–§3, his answers to our three questions.** He calls them *"my thoughts"*, but they are
  specific enough to build from. They are recorded as a decision in
  [../decisions/2026-11-13-samsara-link-asset-field-security-dmv-make-code-brian.md](../decisions/2026-11-13-samsara-link-asset-field-security-dmv-make-code-brian.md).
- **§4–§5, his cleanup plan.** It is **not decided.** In Brian's words: *"I'm in the process of
  reviewing this to get ideas and create a proposed plan. Then will share with others to see what
  they think before making any big changes."* The images are output from a research tool (a
  `zendesk` citation chip on one claim), and CodingCops has not re-measured them.

Opening line, verbatim: *"The biggest issue with our Samsara account seems to be that we were not
following the proper procedures when "moving a gateway" from one vehicle to another…"*

## 1. Q1 — External IDs: the ERP writes them, and the link works both ways

Verbatim:

> *"I'll provide you with the initial "linked" vehicles.*
>
> *For the ERP… definitely not by hand… ERP would do this automatically. User could select from a
> smart-list of known "unlinked" vehicles the ERP knows exists in Samsara. When user links an
> "unassigned" Samsara vehicle (in the ERP) then the ERP will write the ERP's asset ID into
> Samsara.*
>
> *The ERP will store the Samsara ID, so the link will work in both directions.*
>
> *And a report/queue can be created with a daily check to notify us of any Samsara vehicles with
> no linking ERP asset… ERP assets (with engines) that have no Samsara link… and Samsara reads the
> VIN directly from the engine, so we should also check linked vehicles where the VIN in ERP no
> longer (or doesn't match) the VIN in Samsara."*

| Ask | Built today (read 2026-11-13) |
| --- | --- |
| Brian supplies the initial linked vehicles | **A slot exists:** `apps/api/fcc-seeder/seed-files/samsara-asset-map.json` holds 52 *provisional* links (FCC unit code → Samsara id) taken from FCC's `LowerGPSID` on 2026-10-20, and the seeder applies them. Brian's list would replace that provisional map. |
| Picker of unlinked Samsara vehicles | **Partly.** The asset form has a Samsara picker, and a link already in use is refused (`assets.service.ts:520`, *"That Samsara asset is already linked to another asset"*). Whether the picker hides already-linked vehicles was not checked. |
| ERP writes **its asset ID** into the Samsara External ID when a link is made | **Not built.** The ERP never writes to Samsara. This needs a Samsara token that can edit vehicles, from Patrick McKiernan. Whether the current token can write was not checked. |
| ERP keeps the Samsara ID | **Built:** `Asset.samsaraAssetId`. |
| Daily check with notification: (a) Samsara vehicles with no ERP asset; (b) ERP assets **with engines** that have no Samsara link; (c) linked pairs whose VINs differ | **Not built.** Rule (b) needs a way to tell which assets have engines; nothing defines that yet. |

**Which ERP value goes in the External ID** is settled by §4's *"Asset ID: generated by the
system, never changes … Samsara (through its External IDs field), QuickBooks and ADP all link on
this"*. That is `Asset.id`, the UUID, not the unit code.

## 2. Q2 — an "Asset Data Admin" role with field-level edit rights, change history and approvals

Verbatim:

> *"This could be a special role in the ERP… like "Asset Data Admin" role. Could the ERP handle
> multiple roles for the same user? That would work nice, I think, and would make it possible to
> easily/efficiently add a role like "Asset Data Admin" for this purpose.*
>
> *Similar to payroll, this will require field-specific security/access… controlled by a user role
> in the ERP. We assign specific users to that role that would be able to make changes to specific
> fields and/or be able to view certain fields.*
>
> *The special fields for assets that could be edit-controlled could include things like: Asset
> Code, VIN, crane serial number, license plate and state, Samsara link, active/sold status,
> owned/rented*
>
> *… and I'm thinking we will have a few "finance/accounting-related" fields like this as well… and
> possibly need similar functionality for certain types of attached/uploaded files/documents. we'll
> have to figure out the best way to handle this… I was thinking it could be a separate
> card/section in the asset module (I'm thinking that might make it easier to contain those
> "special" fields, while still allowing others to "view" or be hidden).*
>
> *And, especially for these "special/controlled" fields, we will need history/monitoring to more
> easily see if/when changes are made.*
>
> *Log every core-field change (who, when, old/new value). VIN, serial and Samsara-link changes
> also need a reason, a photo of the data plate or registration, and a notification to the other
> admins. Asset Code changes and retiring or merging records need a second admin's approval.
> Please also validate VINs (17 characters, no I/O/Q, check digit) and block duplicate VINs
> (although Samsara might not even allow this) and duplicate Samsara links."*

| Ask | Built today (read 2026-11-13) |
| --- | --- |
| A user holding more than one role | **No.** A user has one `role` (`USER`/`ADMIN`/`SUPER_ADMIN`). An employee can be given **extra access per module** (`EmployeePermissionGrant`: module plus view/create/edit/delete, with who granted it and a note). This is the closest thing to an add-on "Asset Data Admin", but it works per module, not per field. |
| Field-level edit and view rights on assets | **Not built.** One `asset-management: edit` permission covers every field (`assets.controller.ts:103-104`). |
| Log every core-field change: who, when, old and new value | **Built for asset edits.** `assets.service.ts` writes a field diff to `ActivityLog` on each update (`resolveFieldDiff(computeFieldDiff(…))`, around line 591), including `unitCode`. Whether every core field named above appears in that diff was not checked field by field. |
| Reason, photo and notification for VIN, serial and Samsara-link changes | **Not built.** |
| Second admin's approval for Asset Code changes and for retiring or merging records | **Not built.** There is no merge of asset records at all. Archiving already exists (`asset-management: archive`). |
| VIN validation (17 characters, no I/O/Q, check digit) | **Not built.** `vin` is optional free text, up to 100 characters (`create-asset.dto.ts:203-207`). |
| Block duplicate VINs | **Not built.** |
| Block duplicate Samsara links | **Built**, per tenant (`@@unique([tenantCompanyId, samsaraAssetId])` and the service check above). |
| Fields named: Asset Code, VIN, crane serial, plate and state, Samsara link, active/sold status, owned/rented | All exist on `Asset`: `unitCode`, `vin`, `serialNumber`, `license`/`state`, `samsaraAssetId`, `status`, `companyOwner`. Whether `companyOwner` is the owned/rented flag was not checked. |

**Tension with a recorded decision.** The verified decision of 2026-10-20 says that *one main
role* decides access
([../decisions/2026-10-20-departments-roles-main-role-and-can-also-fill-corrina.md](../decisions/2026-10-20-departments-roles-main-role-and-can-also-fill-corrina.md)).
Brian's *"multiple roles for the same user"* would grant access from a second role. The per-employee
extra-access grant already built goes beyond that decision too, so the code has stretched it
already. The question is filed in
[../admin/gaps.md](../admin/gaps.md#field-level-edit-rights-on-asset-identity-data--pointer-owned-by-assets).

**Who goes in the role.** Brian's reply does not settle the five-person list from 2026-11-12. He
deferred that to Joe Schacatano and Kyle Harlow, and they have not answered.

## 3. Q3 — DMV make code: a lookup list, in a Registration section, only for registered assets

Verbatim:

> *"I think this should be one of those fields that has a configuration table in the ERP with the
> known DMV Make codes.*
>
> *Only for registered assets, so we might need a checkbox for the user to select if it is to be
> registered… Hidden on unregistered items like radios, rigging and forklift. Pretty sure this Make
> Code would simply display in the user interface for reference, but would simply pull (or be
> driven from) the selected Make that the user selects.*
>
> *Please put it in a Registration section with plate, state and expiry. Required when a plate
> exists (trailers included), hidden otherwise. It should be entered from the registration card,
> with a suggested default from the Make list and a flag if they differ."*

Settled: a **configuration table** of DMV make codes; the field sits in a **Registration section**
with plate, state and expiry; it applies **only to registered assets**, trailers included.

**Two places where the reply contradicts itself**, both affecting what users see:

- **What shows the field.** A *"checkbox … if it is to be registered"*, or *"required when a plate
  exists … hidden otherwise"*.
- **Where the value comes from.** *"Simply display … driven from the selected Make"* (read-only,
  taken from the Make), or *"entered from the registration card, with a suggested default from the
  Make list and a flag if they differ"* (entered by a person, pre-filled, checked against the
  Make).

The second reading of each is the later and more detailed of Brian's two paragraphs, so it may
be his refinement. That is inference. Today the ERP has `license`, `state` and `expiryDate` on
`Asset`, and no make-code field or table.

## 4. The cleanup plan: findings (research output, not re-measured)

**Six gateways were moved between trucks, and the Samsara record was renamed instead of moved.**
Verbatim: *"crane 10004 is using tractor AT07's old gateway and still carries AT07's VIN. SL03,
SL04, ST12, "4.24 Stakebed" and the Re Rent duplicate came from AT03, AT05, 2202, 2203 and AT06.
Samsara's guidance is that when you move a gateway from one vehicle to another and need to
maintain historical vehicle records for HOS or IFTA purposes, review how to Move a Vehicle
Gateway from One Vehicle to Another. That step was skipped, so those trucks' trip histories are
now mixed together."*

- This **confirms the inference** in
  [fcc-samsara-reconciliation-2026-09-21.md](fcc-samsara-reconciliation-2026-09-21.md) that the
  four FCC ID collisions are moved gateways. All four pairs match: `10004`/`AT07`, `SL03`/`AT03`,
  `SL04`/`AT05` and `ST12`/`2202`. The source is Brian's research, not a physical check.
- *"Samsara's "MT01 - Kyle Harlow" is FCC's FBT 2.12. FCC's MT01 is a different, brand-new F-550
  that isn't in Samsara at all. If you'd renamed Samsara records before comparing, you'd have made
  new mistakes."*

**Fix now** (verbatim list, TCG's own data work): *"In Samsara, correct the wrong VINs on 9002 and
10004. Deactivate the gateways on units FCC marks inactive (UT03, 6001, the Re Rent duplicate).
Clear the two carrier overrides. In FCC, fix the VIN typos on 4003, 4004, AT21 and MT01 (it has a
letter O where a zero belongs). Fix the status on SL03, SL05 and RE-RENT PT2. FCC says they're
inactive, but they're still driving. Read 55001's data plate. FCC and Samsara have two different
VINs for it, and both pass the check-digit test."*

- `4003`, `4004`, `AT21`, `9002` and `55001` match our 2026-09-22 adjudications. `MT01` is new.
- **Corrected by Brian the same day (§6):** `SL03` and `SL05` are self loaders TCG no longer
  owns. They left with their Samsara devices still connected, so FCC's *inactive* is right and
  the "fix the status" item is wrong for them.
- *"Wait on any renaming until the code standard is decided, so nothing gets renamed twice."*
- *"Worth checking soon: 16 active units show a registration expiry in FCC that has already
  passed. Either FCC isn't being updated or the registrations have lapsed."*

## 5. The cleanup plan: unit codes and fields (proposed, not decided)

**Two IDs instead of one.** FCC's UnitCode currently identifies equipment, names trailers after
their crane, and also holds cost categories (`SAFETY 01`, `TIRES 01`, `SHOP/YARD`), placeholders
(`275 TON`, `CR`) and dead records (`DELETE`, `PT02 - DUPLICAT`). The plan splits it:

- **Asset ID:** *"generated by the system, never changes, never reused, never seen by employees.
  Samsara (through its External IDs field), QuickBooks and ADP all link on this."* **This is the
  ERP's design already:** `Asset.id` is a UUID, and the business code is separate (CLAUDE.md →
  *Identity*).
- **Unit Code:** *"the human label painted on the equipment. It must be unique, changes rarely, and
  every change is logged so people can still search by the old code."* Built today: `unitCode` is
  unique per tenant, and changes are in the activity-log diff. **Searching by an old code is not
  built.**

**Suggested Unit Code rules:** capital letters and numbers only, with no spaces, slashes or
periods; no names, statuses or notes (*"Sold"*, *"OLD"*, driver names); never reuse a retired
code; physical assets only, with cost categories moving to the ERP's job and cost codes; the code
does not say which crane a trailer works with. Keep the crane numbering (capacity plus sequence:
`10001`, `26502`, `55001`) and the support-fleet prefixes (`AT`, `SL`, `ST`, `PT`, `MT`, `SV`).
Normalise the stragglers (`UT-1` → `UT01`, `FBT 1.12` → a plain code). **Trailers get a
permanent code by type** (e.g. `TROL01`, `TRBD01`), and the crane they serve becomes a separate
**assignment** (*"Support Load 1 for 26502"*). Evidence given: `10001 OL` has *"Old Trailer #
10002.1"* in its model field, and `11001 OLD OL` is named `20001 OL`.

**Where codes change:**
- **FCC:** do not renumber, because FCC is being retired and UnitCode is probably linked to work
  orders and invoices (*"Section 3 of the script will show how many tables depend on it"*). Clean
  the data, leave the codes.
- **ERP:** *"load new codes at go-live, with a searchable "Legacy FCC Code" field."* Not built.
- **Samsara:** *"rename the records and set External IDs in one pass at go-live. Renaming doesn't
  lose history, because Samsara ties history to its own internal ID."*
- One cutover date, with a printed list of old and new codes and the decals updated at the same
  time.

**Data you can verify with the manufacturer.** Give each component its own fields and name the
document it is checked against:

| Component | Fields | Checked against |
| --- | --- | --- |
| Truck chassis | VIN, make, model, model year, GVWR | Title, registration card, federal VIN decoder |
| Crane | Make, model, serial, capacity as the manufacturer publishes it | Crane data plate, manufacturer's load chart |
| Engines and transmission | FCC's existing upper and lower engine fields | Engine data plates |
| Registration | Plate, state, expiry | DMV registration card |

- *"Make should be a pick-list, not free text. FCC currently has 6 spellings of Link-Belt and 5 of
  Freightliner."* Today `Asset.manufacture` and `Asset.vehicleMake` are free text. A tenant
  `Manufacturer` table exists, but only parts use it.
- *"Model year should come from the VIN. FCC has AT22–AT31 as 2020, but their VINs say 2021."*

## 6. Teams follow-up, 2026-11-13: the code table, asset-to-asset assignment, and FCC's UnitCode

Brian Petros posted to CodingCops on Teams the same day: *"I'm putting together a plan for
standardizing the Asset codes for the ERP … I haven't shown to Joe or Kyle yet, so it's not
official. I'm showing to you because it involves the ERP having the functionality to "assign" an
asset to another asset."* He attached a code-pattern table. **Not official.**

**The code table** (abridged; every row is *FCC → proposed*):

| Pattern | Used for | Examples | Note |
| --- | --- | --- | --- |
| All codes | Every physical asset | — | Capital letters and numbers only: no spaces, hyphens, slashes or periods. No names, status words or notes. Never reused. Rigging keeps its size-based codes for now. |
| Two IDs | Every asset in the ERP | — | A hidden, permanent Asset ID links Samsara (External ID), QuickBooks and ADP. The Unit Code is the painted label; a change is logged and the old code stays searchable. |
| **Assignment (field in ERP)** | Trailers, radios | `26502.1` → `TRSP02`, *assigned to 26502 as Support Load 1* | *"Which crane a trailer or radio works with is its own field, so moving it never changes its code."* |
| Retired units | Sold or inactive | `AT07`, `2202`, `9001 OL` (unchanged) | Migrate as history under their FCC code. No new code. |
| Capacity + 2-digit sequence | Mobile cranes, boom trucks | `26502`, `4001`, `55001` (unchanged) | |
| `RT` / `CC` + capacity + sequence | Rough-terrain / crawler cranes | `RT9001` (unchanged); `CC330.01` → `CC33001` | |
| `TWC` + 3 digits · `SL##` · `AT##` | Tower cranes · self loaders · assist tractors | unchanged | |
| `ST## PT## MT## UT## SV##` | Sales/yard, pilot, service, utility/parts trucks, cars and SUVs | `UT-1` → `UT01`; `ST11 - WES` → `ST11`; `TRG01` → `MT06` | Driver names come out of the code. |
| `FB##` | Flatbed trucks | `FBT 1.12` → `FB01`; `FBT 4.24` → `FB04` | |
| `TROL## TRSP## TRBD##` | Operator loads, support/counterweight loads, boom dollies | `26503 OL` → `TROL12`; `27501.2` → `TRSP09`; `35001BD` → `TRBD08` | Numbered in crane order. |
| `TRFB## TRLB## TRDD## TRSD## TRCH##` | Flatbed, lowboy, drop deck, stretch deck, chassis trailers | `SD02` → `TRSD02`; `CHAS T3` → `TRCH03` | |
| `RR` + owner's unit number | Rented and re-rented units | `Q56381` → `RRQ56381`; `RE-RENT RT9001` → `RRRT9001` | The owner's painted number stays visible. |
| `MB## MAT## FL## FT## FE## PF##` | Man and material baskets, forklifts, fuel tanks, attachments | `TCGMB01` → `MB01`; `FL-01` → `FL01` | |
| `R###` | Radios | `R0120` → `R120`; `R49` → `R049` | Assigned crane or person moves to its own field. |
| `SB## SP… WM…` | Rigging | unchanged | Decide later whether rigging lives in a separate tool register. |
| (no unit code) | Cost and work categories | `SAFETY 01`, `TIRES 01`, `SHOP/YARD`, `NON-BILLABLE` | Become ERP cost / work-order codes, not assets. |

**Asset-to-asset assignment, proposed and then rejected the same day.** Brian proposed it:
*"we have the trailer "Unit Code" in FCC include the number of the asset it is assigned to … the
"Unit Code" is serving two purposes … in the ERP, the Asset Code should be unique (and then we
have an "Assigned to" field that designates which asset the trailer is currently assigned to)."*
He said Kyle and Jeff are working on this, because *"we don't have enough trailers sometimes and
need to shift trailers around"*. He then reported Kyle Harlow's view, verbatim: *"Kyle said it
makes sense to assign an employee to an Asset, but it doesn't make sense to assign an Asset to
another Asset. He said that maybe 90% of the time, some Assets with go on a job with other
Assets, but they get switched around enough for this "official" assignment of Asset to Asset
doesn't make sense."*

- **Reading:** Kyle Harlow (VP Fleet & Field Ops), relayed by Brian, is against a durable
  asset-to-asset assignment. The table's *Assignment* row and its radio note predate his view and
  are not withdrawn in writing. Kyle **is in favour of assigning an employee to an asset**, which
  nothing in the vault specifies yet.
- **Built today (read from the schema 2026-11-13, not checked on screen):** a job's resources form
  a tree (`JobResource.parentId`: a crane with its support loads under it), and each shift's
  allocation puts a specific asset on each resource (`JobResourceAllocation.assetId`). So the
  ERP already records which trailer went with which crane **per job**, which is the pairing
  Kyle describes. No asset-to-asset or employee-to-asset field exists on `Asset`.

**SL03 and SL05, verbatim:** *"These are two self loader that we no longer have/own. They left
the yard with the Samsara traking device still connected to the engine. That is why they are
"inactive" in FCC, but Samsara still records them as "running". We will be getting those Samsara
tracking devices back at a later date (and I'm thinking they will be used for other vehicles, so
we will eventually reassign those to different assets)."* FCC's status is right. When the devices
come back and are reassigned, that is the gateway move that §4 says was skipped before.

**FCC's UnitCode is its primary key, verbatim:** *"The way FCC database is designed, there is no
"hidden" ID for the units/assets (the Unit Code is the primary ID). So, we should not change the
UnitCodes in FCC… it will cause too much of a cascading change throughout the system. So, I'll be
keeping the UnitCodes in FCC the same… but planning on updating to updated Asset Codes (for some)
in the ERP. Most will/can stay the same, but some will need to change to better standardize. I
think the ERP should have a field for the "FCC UnitCode" so we can link back to FCC historical
data and reference for the users."*

- This makes §5's *"Legacy FCC Code"* field Brian's direct ask, here called *"FCC UnitCode"*.
  Not built. Today the seeder loads FCC's UnitCode into `Asset.unitCode` (renamed only if two
  collide; `apps/api/fcc-seeder/src/seed-all.ts`, `createFleetAsset`) and keeps no separate copy, so
  renaming an ERP code would lose the link back to FCC.
