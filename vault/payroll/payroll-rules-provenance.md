# Payroll rules — provenance register

**What this is.** One row per payroll rule: what we are building, whether it is confirmed, and
**the exact source that confirms it** — who said it, where, when, and at what timestamp or
clause — so that "are we right?" is answered by pointing, not by remembering. Rules are grouped
the way payroll people think about them, not by `PAY-` number.

**Status vocabulary.**
- **Confirmed** — a named human at TCG (or the union) settled it on the record. The source is
  cited. Build from it.
- **Contract** — stated in the Local 12 agreement; no TCG ruling needed unless practice differs.
- **Legacy** — read out of Brian's Payroll App (the 2026-08-18 extract / 2026-09-07 backup);
  nobody at TCG has said it out loud. Usually right, never a ruling.
- **Pending** — asked, no answer yet. The owner is named.
- **Contested** — two TCG-side sources disagree. Both are cited.

**How to cite a source.** Calls are `meetings/<date>` with the transcript timestamp; Teams
messages are `<person>, Teams, <date>`, quoted verbatim in the linked note; the agreement is
`MLA Art. <n> <heading> §<n>`; legacy config is the table and row. Every source below resolves
to a file in this vault.

> ## Changing a rule? Add the source first.
>
> This file is only worth something while every row can be traced. **Nobody edits a rule here —
> or in `rules/PAY-*`, or in the engine — without adding the source that authorises the change**:
> who said it, in which channel, on which date, at which timestamp or clause, with a link to the
> file that holds the verbatim quote. A change with no source is not a rule change; it is a guess
> with a commit hash. If the source is a call, curate the note and cite the timestamp. If it is a
> Teams message, quote it verbatim in the decision note or the register entry and cite that. If it
> is your own reading of the contract, cite the clause and mark the row *Contract*, not
> *Confirmed*. And if you are changing a *Confirmed* row against its source, the new source must
> outrank the old one (see the table at the end) — otherwise open a *Contested* row and leave both.
>
> The same applies in reverse: when a client message or call settles something, the row here
> changes **in the same commit** as the decision note or rule file. A rule the engine implements
> that this register cannot trace is a defect, whichever way the money falls.

whether the engine *does* each rule; [rules/](rules/INDEX.md) for the full history per rule;

| Money rounding to cents (PAY-069) | **Legacy** | The legacy Payroll App rounds in SQL Server `decimal` — T-SQL `ROUND(x, 2)`, which is **half away from zero** on both signs. That behaviour is the measuring stick for the July 25–31 golden-week parallel run, so the engine matches it. `Math.round(n * 100) / 100` did not: it rounds half toward +∞, under-deducting a penny on an exact negative half (reachable — PAY-046 posts the meal deduction with −0.5 h), and `n * 100` reintroduced binary-float error that put `1.015`, `10.075` and `0.145` a cent low on either sign. The snap repairs float products such as `1.5 × 16.33 = 24.494999…`, which arrive already carrying the error; the shift repairs literals like `1.015`. It matches T-SQL for any amount a pay figure or four-decimal rate can hold within 15 significant digits. It is not arbitrary-precision decimal. Pinned in `packages/payroll-engine/src/money.spec.ts`; the snap and `-0` handling were added in app commit `0952501a2` after PR #657's review. Nobody at TCG has ruled on rounding *method* for money; this is legacy behaviour matched, not a ruling. | — |
