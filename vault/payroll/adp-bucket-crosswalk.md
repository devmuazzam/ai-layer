# Payroll Bucket to ADP Import Crosswalk — Draft v1

> **Observed on the ADP side, 2026-08-18.** The Workforce Now ROLL worksheet for company 4RZ
> shows these fields as named columns — Reg Hours, OT Hours, DT Hours, Holiday 2x/3x Hours,
> Shift Diff 2/3 (code, amount), **Temporary Rate with LB REG / LB OT / LB DBL / LB TRI**, SUB
> PAY, Sick, P.T.O. — with one extra row per distinct boom adder (the temp rates equal the legacy
> app's `OI-BP/OP-BP` bracket values). Batches are marked *Manual Entry*. Layout and the legacy
> figures that feed each column: [legacy-payroll-app-db-extract/INDEX.md](legacy-payroll-app-db-extract/INDEX.md).


Prepared 2026-08-05. Developer-facing source of truth for how ERP payroll components are
translated into ADP paydata fields and Hours/Earnings codes.

## Current-state basis

Rows marked **CURRENT** reflect the existing Excel/Power Query ADP export design. Rows marked
**APPROVED DESIGN** reflect current Payroll App rules that can reuse the existing ADP field/code
while preserving the more detailed reason in the ERP component ledger. Rows marked **TBD** require
an ADP validation-table code and payroll/HR confirmation of taxability, accumulators, and whether
the code is included in total hours worked.

> **Identifier warning.** The current paydata workbook uses ADP **Co Code 4RZ**. A separate ADP
> validation-table export previously showed **Company Code 631**. CodingCops should treat these as
> different ADP identifiers until ADP confirms their intended contexts; **do not substitute one for
> the other.**

## Recommended system design

Store this mapping as effective-dated configuration, not hard-coded `CASE` statements. The ERP
component ledger remains the audit truth; the ADP export aggregates components according to this
crosswalk.

| Status | Meaning |
| --- | --- |
| CURRENT | Already represented by the current ADP export workbook; still verify code setup in the live ADP validation table. |
| APPROVED DESIGN | New ERP component can aggregate to an existing ADP field/code without losing audit detail in the ERP. |
| TBD | Requires an ADP code/configuration or payroll-policy decision. |
| OUT OF SCOPE | Not generated by the current hourly paydata import. |

## CodingCops implementation rules

**1. Configuration over code** — Persist the crosswalk in an effective-dated configuration table. Do not embed ADP mapping logic in multiple stored procedures, API endpoints, or UI components.

**2. ERP ledger remains the audit truth** — Keep detailed component reasons such as daily OT, weekly OT, seventh-day OT, guarantees, rest premium, and WTL in the ERP pay-component ledger even when several components aggregate to one ADP field.

**3. Primary ADP row** — Create one primary ADP row per employee/pay period for Reg Hours, O/T Hours, DT, HDD, HOL, SUB, and SIC as applicable.

**4. Temporary-rate rows** — Create one temporary-rate row per unique ADP File Number + ADP code + Temp Rate. Populate only one Hours 4 code/amount pair on each such row.

**5. Paired fields** — Never send a Hours/Earnings code without its paired amount/hours, or an amount/hours without its code.

**6. Zero handling** — Omit zero-value code/amount pairs from the CSV. A zero should not create an ADP payroll component.

**7. Validation table** — Before export, validate that every ADP code is active in the company validation table and that the row uses the correct ADP field group.

**8. File number** — ADP File Number is text, preserves leading zeros, allows uppercase alphanumeric characters, has a maximum length of 6, and must be unique among active mappings.

**9. Payroll group exclusions** — System-Testing-VendorAccess employees are excluded. Non-Union Admin Salary does not use the hourly nonexempt import path.

**10. Non-union overtime** — The legal workweek is Saturday-Friday. Daily, weekly, and seventh-day rules are calculated in the ERP without pyramiding/double counting; ADP receives the resulting OT/DT totals.

**11. Non-worked premiums** — Rest and missed-meal/WTL premiums should not inflate worked-hour totals. Configure the ADP code accordingly.

**12. Effective dating** — Every mapping must support effective start/end dates so future ADP code changes do not rewrite historical payroll exports.
